# Culinary Craft

Учебное приложение для рецептов и кулинарного сообщества.
Стек проекта — React 18, Vite, Spring Boot 3.5.7 и PostgreSQL 17.

## Запуск с нуля на Windows

### 1. Установите инструменты и выберите ветку

На Windows проверены Temurin JDK 21.0.11, Node.js 22.15.1, npm 10.9.2,
Git 2.52.0 и Docker Desktop 4.49.0 с Engine 28.5.1 и Compose v2.40.2.
Для запуска удобно взять актуальные патчи JDK 21 и Node.js 22. Требуется
Node.js 22.12 или новее в ветке 22. npm поставляется с Node.js. Gradle Wrapper
скачает версию Gradle из проекта. Python 3 нужен для локальной сборки метрик.

Запустите Docker Desktop в режиме Linux containers и дождитесь готовности Engine.
Проверьте инструменты в PowerShell:

```powershell
java -version
node --version
npm.cmd --version
git --version
docker version
docker compose version
```

```powershell
git clone https://github.com/asakkyy/culinary-craft.git
Set-Location culinary-craft
git switch dev
```

`dev` содержит интегрированную версию с PostgreSQL, аккаунтами, модерацией и
редизайном. `main` публикует релизы и может отставать от `dev`. Для проверки
черновиков этого этапа до его интеграции переключитесь на
`git switch --track origin/feature/final-stabilization`.

### 2. Терминал 1 — PostgreSQL, Mailpit и backend

В корне репозитория установите зависимости Git hooks:

```powershell
npm.cmd ci
```

Задайте параметры новой локальной базы. Выберите собственный пароль и сохраните
его для повторных запусков с этим volume. PowerShell скрывает ввод пароля:

```powershell
$env:POSTGRES_DB = 'culinary_craft'
$env:POSTGRES_PORT = '5432' # Если 5432 занят, укажите '55432'.
$env:DB_USERNAME = 'culinary_demo'
$dbPassword = Read-Host 'Пароль локальной PostgreSQL' -AsSecureString
$env:DB_PASSWORD = [Net.NetworkCredential]::new('', $dbPassword).Password
Remove-Variable dbPassword
$env:DB_URL = "jdbc:postgresql://127.0.0.1:${env:POSTGRES_PORT}/${env:POSTGRES_DB}"
$env:MAIL_PORT = '1025'
$env:MAILPIT_WEB_PORT = '8025'

docker compose up -d --wait postgres mailpit
docker compose ps
```

Compose оставляет внутренний порт PostgreSQL 5432 и публикует его на
`127.0.0.1:$env:POSTGRES_PORT`. При переносе на 55432 задайте этот порт перед
запуском Compose и пересчитайте `DB_URL` той же строкой. При повторном запуске
используйте исходные имя базы, пользователя и пароль. Переменные
инициализации действуют при первом старте с пустым volume.

В том же терминале подготовьте JVM-процесс и первого администратора:

```powershell
$keyBytes = New-Object byte[] 48
$random = [Security.Cryptography.RandomNumberGenerator]::Create()
try { $random.GetBytes($keyBytes) } finally { $random.Dispose() }
$env:JWT_SECRET = [Convert]::ToBase64String($keyBytes)
Remove-Variable keyBytes, random
$env:COOKIE_SECURE = 'false' # Локальный HTTP. Через HTTPS используйте true.
$env:MEDIA_ROOT = Join-Path $PWD.Path 'backend/data/media'
$env:MEDIA_CLEANUP_ENABLED = 'false'
$env:MAIL_HOST = '127.0.0.1'
$env:MAIL_AUTH = 'false'
$env:MAIL_STARTTLS = 'false'
$env:MAIL_FROM = 'culinary@example.test'
$env:PUBLIC_APP_URL = 'http://127.0.0.1:5173'

$env:BOOTSTRAP_ADMIN = 'true'
$env:ADMIN_EMAIL = Read-Host 'Email первого администратора'
$adminPassword = Read-Host 'Пароль администратора (16–64 символа ASCII)' -AsSecureString
$env:ADMIN_PASSWORD = [Net.NetworkCredential]::new('', $adminPassword).Password
Remove-Variable adminPassword

Set-Location backend
.\gradlew.bat bootRun
```

`JWT_SECRET` должен содержать минимум 32 случайных байта в Base64. Храните ключ
и пароли вне Git. Для сохранения сессий при повторных запусках используйте тот
же JWT-ключ из защищённого окружения. Новый ключ отзывает выданные сессии.
Compose читает `.env`. Spring Boot получает переменные из окружения процесса,
поэтому значения из `.env` нужно отдельно передать в терминал backend.
В уже открытые окна PowerShell переменные автоматически не передаются.

Bootstrap создаёт подтверждённого ADMIN только при отсутствии активного ADMIN.
Существующему USER роль не повышается. После первого входа в
`http://127.0.0.1:5173/login` по выбранным email и паролю откройте
`http://127.0.0.1:5173/admin`. Остановите backend через Ctrl+C и отключите
bootstrap перед следующим запуском из `backend`:

```powershell
$env:BOOTSTRAP_ADMIN = 'false'
Remove-Item -LiteralPath Env:ADMIN_EMAIL, Env:ADMIN_PASSWORD -ErrorAction SilentlyContinue
.\gradlew.bat bootRun
```

Если активный ADMIN уже существует, запускайте с отключённым bootstrap и
используйте его учётную запись. Для восстановления пароля выберите
«Забыли пароль?» на странице входа, укажите текущий email администратора и
откройте письмо в Mailpit. После сброса войдите с новым паролем.

### 3. Терминал 2 — frontend

Откройте второй PowerShell в корне того же репозитория:

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd run dev
```

Приложение работает на [127.0.0.1:5173](http://127.0.0.1:5173), Mailpit на
[127.0.0.1:8025](http://127.0.0.1:8025). Vite проксирует `/api` на backend.
Из любого терминала проверьте, что backend запустился и вернул
`storage = POSTGRESQL`:

```powershell
Invoke-RestMethod http://127.0.0.1:8080/api/health
```

Для остановки используйте Ctrl+C в обоих терминалах и `docker compose stop`
из корня. `docker compose down` удаляет контейнеры и сохраняет именованный
volume `postgres_data`. Для обычной остановки выбирайте команду без `-v`.

### 4. Сценарий демонстрации

1. Зарегистрируйте обычного пользователя. На странице подтверждения нажмите
   «Отправить письмо». Регистрация сама письмо не отправляет.
2. Откройте письмо в Mailpit, перейдите по ссылке и нажмите «Подтвердить email».
   Пользователь вернётся в профиль. Для сброса пароля используется отдельная
   форма `/forgot-password` и отдельное письмо.
3. Нажмите «Добавить рецепт», заполните форму и выберите фото PNG или JPEG
   до 5 МБ. Отправьте рецепт на модерацию.
4. Войдите как ADMIN в отдельном профиле браузера или приватном окне.
   Откройте `/admin`, найдите рецепт в очереди и одобрите его.
5. В пользовательском окне найдите рецепт в каталоге, добавьте его в избранное
   и отправьте жалобу. В панели ADMIN рассмотрите жалобу и проверьте событие
   в разделе аудита.
6. Откройте редактор, измените текст и уйдите через «Сохранить черновик и выйти».
   При следующем открытии выберите «Восстановить черновик» и сверьте текст.
   Новое локальное фото потребуется выбрать заново. Уже загруженное фото
   остаётся на сервере.

### 5. Если запуск остановился

| Симптом | Проверка и действие |
| --- | --- |
| Docker не отвечает | Запустите Docker Desktop, выберите Linux containers, повторите `docker version` до появления раздела Server. |
| Порт PostgreSQL занят | Задайте `POSTGRES_PORT=55432` в терминале 1, пересчитайте `DB_URL`, повторите запуск Compose. |
| Backend не подключается к БД | Сверьте `docker compose ps`, порт и имя базы в `DB_URL`, затем пользователя и пароль исходного volume. |
| Backend требует JWT или данные ADMIN | Задайте `JWT_SECRET` и оба параметра ADMIN в терминале backend. Для существующего ADMIN отключите bootstrap. |
| Письмо не приходит | Нажмите «Отправить письмо» и проверьте Mailpit, `MAIL_HOST`, `MAIL_PORT`, `MAIL_FROM`, `MAIL_AUTH` и `MAIL_STARTTLS`. Повторный запрос доступен после паузы. |
| Ссылка из письма недействительна | Запросите свежее письмо для текущего email. Откройте его по `PUBLIC_APP_URL`, который использует браузер. |
| Frontend не видит backend | Проверьте `/api/health` на 8080 и используйте `127.0.0.1:5173` в браузере. Для HTTP проверьте `COOKIE_SECURE=false`. |
| Порт 8080 или 5173 занят | Выполните `Get-NetTCPConnection -State Listen -LocalPort 8080,5173`. Проверьте `OwningProcess` и остановите свой старый сервер, чтобы сохранить адреса Vite и backend. |
| Java Language Server показывает ошибки | Сверьте `JAVA_HOME`, выполните `.\gradlew.bat --version` и `.\gradlew.bat compileJava` из `backend`. В VS Code обновите Gradle-проект или выполните «Java: Clean Java Language Server Workspace». |
| Flyway остановился | Прочитайте первую ошибку в журнале backend, сверьте базу из `DB_URL`, историю `flyway_schema_history` и права на `pg_trgm`. Для рабочей базы сначала сделайте резервную копию и исправьте причину по истории миграций. |

## Усиление безопасности

V6 добавляет общие для экземпляров приложения PostgreSQL-счётчики попыток:
вход — 30 запросов на IP и 10 на email за 10 минут, регистрация — 10 на IP
за 10 минут. Неуспешные запросы также учитываются, HTTP 429 содержит Retry-After.
Идентификаторы окон хешируются, старые окна удаляются через два дня.
X-Forwarded-For не доверяется; за reverse proxy потребуется отдельно настроить
доверенную передачу клиентского IP (иначе лимит разделяют клиенты одного proxy).
Cookie сессии и CSRF используют SameSite=Strict и Secure по COOKIE_SECURE.
COOKIE_SECURE=false допустим только для локального HTTP. Сообщения внутренних
ошибок, stacktrace и rejected values не включаются в стандартные ответы Spring.

Рецепты, отзывы, избранное, аккаунты, жалобы и аудит сохраняются в PostgreSQL.
Реализованы Auth & Security, настройки профиля, аватары и фото рецептов,
пользовательские жалобы, административное рассмотрение, блокировки и аудит.

## Аккаунты и сессия

Новая миграция V3 расширяет существующую таблицу пользователей, сохраняя ID и
все связи. Старые пользователи имеют статус LEGACY без email и пароля; войти
под ними нельзя. Новые ID начинаются с 1001. Регистрация не передаёт новым
аккаунтам старые рецепты и всегда создаёт USER, даже если клиент прислал роль.
Заголовок `X-Demo-User` больше не аутентифицирует запросы.

API: `POST /api/auth/register` (201), `POST /api/auth/login`, `GET /api/auth/me`,
`POST /api/auth/logout`, `GET /api/auth/csrf`. Формы доступны на `/register`,
`/login` и через кнопку аккаунта. Защищённые маршруты направляют гостя на вход.
Пароль регистрации: 12–64 символа и не более 72 байт UTF-8; BCrypt cost 12.
Email уникален без учёта регистра. API не возвращает хеши.

JWT подписывается HS256 библиотекой Nimbus/Spring Security, живёт 30 минут,
проверяет issuer `culinary-craft`, audience `culinary-browser`, подпись и время.
Хранится только в HttpOnly SameSite=Strict cookie `/api`, не в localStorage.
Каждый запрос проверяет статус аккаунта и token_version в БД. Выход отзывает
все ранее выданные сессии аккаунта. Refresh token пока не реализован.
POST/PUT/DELETE требуют CSRF: клиент получает маскированный токен через
`/api/auth/csrf` и передаёт его в `X-XSRF-TOKEN`; JWT cookie не отменяет CSRF.

Подготовка JWT и первого ADMIN описана в [инструкции запуска](#запуск-с-нуля-на-windows).
Bootstrap защищён транзакционной advisory lock. Публичного API назначения ADMIN нет.

Подтверждение email, восстановление пароля и ограничение попыток реализованы.
Пользовательского списка отдельных сессий пока нет. Статус
BLOCKED учитывается валидатором JWT на каждом запросе, API/UI блокировок реализованы.
Не выставляйте учебный сервер в Интернет без дальнейшей защиты.

JUnit генерирует случайный JWT_SECRET только для тестового процесса. Playwright
генерирует собственный ключ и пароль bootstrap-admin и требует отдельный
`E2E_DB_URL`. Он не должен указывать на пользовательскую БД. Для каждого
локального E2E-прогона используйте свежую тестовую базу; CI получает свежий service.
Например, перед `npm.cmd run test:e2e` задайте JDBC URL отдельной базы в
`$env:E2E_DB_URL`. Настоящие ключи и пароли не нужны в GitHub Secrets для тестов.

## Профиль, изображения и администрация

Настройки доступны на `/settings`, профиль — `/profile`, собственные жалобы —
`/reports`. Панель ADMIN находится на `/admin`: рецепты, жалобы, пользователи,
аудит. Существующая `/moderation` сохранена и используется панелью повторно.

| Метод | API | Назначение |
| --- | --- | --- |
| PUT | `/api/account/profile` | `{name}` только текущего пользователя |
| PUT | `/api/account/email` | `{email,currentPassword}`, уникальность без учёта регистра |
| PUT | `/api/account/password` | `{currentPassword,newPassword}`, отзыв всех старых JWT |
| POST / DELETE | `/api/account/avatar` | multipart `file` / удаление своего аватара |
| POST / DELETE | `/api/recipes/{id}/photo` | multipart `file` / удаление обложки владельцем или ADMIN |
| GET | `/api/media/{uuid}` | PNG с проверкой видимости рецепта |
| POST | `/api/recipes/{id}/reports` | `{reason,description}` для опубликованного рецепта |
| GET | `/api/reports`, `/api/reports/{id}` | Только собственные жалобы |
| GET | `/api/admin/reports` | `status`, `search`, `page`, `size` |
| POST | `/api/admin/reports/{id}/decision` | `{status,comment}` |
| GET | `/api/admin/users` | `status`, `search`, `page`, `size` |
| POST | `/api/admin/users/{id}/block` | `{reason}` |
| POST | `/api/admin/users/{id}/unblock` | Восстановить возможность нового входа |
| GET | `/api/admin/audit` | `action`, `page`, `size` |

Имя и email обновляются в Context и хранятся в PostgreSQL. Смена email требует
текущего пароля и повторного подтверждения нового адреса. Роль и статус нельзя
изменить через профиль. После смены пароля требуется новый вход на всех устройствах.
В профиле показываются email, дата регистрации, статус, аватар и собственные рецепты.

### Файловое хранилище

`MEDIA_ROOT` задаёт постоянную директорию backend. По умолчанию это `./data/media`
относительно рабочего каталога процесса, то есть `backend/data/media` при bootRun.
Например, в PowerShell перед запуском backend:

```powershell
$env:MEDIA_ROOT = 'D:\culinary-craft-data\media'
```

Compose сейчас запускает PostgreSQL, backend работает на хосте: файлы остаются
в выбранной локальной директории после перезапуска. При контейнеризации backend
нужно смонтировать её volume/bind mount в этот сервис. Не помещайте изображения
в volume PostgreSQL. Резервируйте БД и MEDIA_ROOT согласованно; один SQL-backup
не содержит файлов. Каталоги изображений и результаты тестов исключены из Git.

Принимаются только декодируемые PNG/JPEG до 5 МБ, до 4096 px по каждой стороне
и 12 млн пикселей. Результат повторно кодируется в PNG и также ограничен 5 МБ.
SVG, текст и исполняемые форматы не принимаются. Исходные имена и пути не используются:
имена генерируются из UUID, публичный ответ содержит только `/api/media/{uuid}`.
Content-Type фиксирован `image/png`, установлен nosniff, выдача без кэширования.
Миниатюры отображаются тем же безопасным PNG с масштабированием в UI.
Физическая генерация нескольких размеров — возможное будущее улучшение.

Сначала записывается временный файл и атомарно перемещается; затем фиксируются
метаданные. При rollback новый файл удаляется. При замене старый удаляется только
после commit. Удаление рецепта очищает его метаданные и файл после commit.
Ошибка удаления логируется по UUID для последующей очистки. Файлы после аварии
обрабатывает MediaCleanupService. Ссылки на незаписанные файлы не коммитятся.
При неизвестном исходе commit (например, потеря соединения) новый файл сохраняется:
удалять его как при подтверждённом rollback опасно. Очистка позднее проверит ссылки.
Недоступность БД во время удаления старого файла после commit также откладывает
удаление, не превращая уже сохранённую загрузку в ошибку ответа.

ADMIN → «Хранилище» → «Проверить без удаления» показывает кандидатов. Endpoint
`POST /api/admin/media/cleanup` требует явный `{dryRun:true}` или `{dryRun:false}`.
Проверяются media_files, recipes.image_url и demo_users.avatar_url; используемые
файлы не удаляются. Только UUID.png и .upload-*.tmp, без симлинков/рекурсивного
обхода, старше MEDIA_ORPHAN_GRACE_HOURS (по умолчанию 24, минимум 24).
Партия ограничена 500 кандидатами. Перед unlink повторно проверяются БД и атрибуты.
Старые фотографии при замене также защищены проверкой оставшихся ссылок.
Импортировать произвольный чужой `/api/media/` URL через RecipeRequest нельзя.

Участники используют общую PostgreSQL advisory lock: загрузки — shared до commit,
очистка — exclusive. Экземпляры приложения должны использовать одну БД и одно
MEDIA_ROOT. Несогласованные ручные изменения каталога/БД этой защитой не покрываются.
MEDIA_CLEANUP_ENABLED=true включает проверку каждый час, начиная через минуту;
MEDIA_CLEANUP_DRY_RUN=true по умолчанию. Для автоматического удаления требуется
явно задать false после просмотра кандидатов и резервирования БД вместе с файлами.
Тесты используют только временное хранилище, автоматический планировщик выключен.

Загрузка, замена и удаление фото возвращают рецепт в PENDING. Изображение такого
рецепта доступно только автору/ADMIN. Аватары публичны, заменять/удалять можно только свои.

### Жалобы, блокировки и аудит

Причины: SPAM, ABUSE, COPYRIGHT, INCORRECT, OTHER. Статусы: OPEN, IN_REVIEW,
RESOLVED, REJECTED. Одинаковая активная причина для пары заявитель–рецепт запрещена
уникальным индексом; разрешено не более пяти новых жалоб в час на пользователя.
Операции сериализуются блокировкой строки пользователя. Заявитель видит только
свои жалобы и статус; внутренний комментарий администратора ему не выдаётся.

ADMIN может взять OPEN в работу, закрыть либо отклонить. Строка жалобы блокируется
на транзакцию; взятую в работу может завершить только назначенный администратор.
Повторное решение и конкурирующее решение другого администратора дают 409.
Очереди, пользователи и аудит фильтруются и разбиваются на страницы в PostgreSQL:
по умолчанию 20 записей, максимум 50, порядок по дате и ID по убыванию.
Для жалоб сохраняется снимок названия/ID рецепта даже после удаления рецепта.

Блокировка запрещает вход и действие ранее выданных JWT. Разблокировка не оживляет
старые токены: требуется новый вход. Публикации автоматически не удаляются.
Самоблокировка и блокировка последнего активного ADMIN запрещены. Изменения
доступности администраторов сериализуются с bootstrap через advisory lock.
Legacy-аккаунты не активируются через блокировку/разблокировку.

Аудит хранит блокировки, разблокировки, принятие/решения жалоб, одобрение и отклонение
рецептов. Журнал доступен только ADMIN; API изменения/удаления аудита нет.
В аудит не передаются пароли, JWT и CSRF. Не вводите секреты в причины/комментарии.

Новые миграции: V4 — media_files; V5 — recipe_reports, administrative_audit,
причина/дата блокировки. V1–V3 не изменены. JUnit проверяет обновление старой БД,
сохранность владения, файлы после двух стартов приложения и конкурентные решения.

## Подтверждение email и восстановление доступа

V7 добавляет email_verified_at и account_email_tokens. Старые USER должны
подтвердить адрес, provisioned ADMIN считается доверенным; LEGACY не активируется.
Вход и собственные настройки доступны до подтверждения, но запись рецептов,
отзывов, избранного и жалоб требует подтверждённого адреса на сервере.
`/api/auth/me` возвращает emailVerified. Регистрация возвращает одинаковый
нейтральный ответ 201 для нового и уже занятого адреса, не раскрывая аккаунт.

Письмо подтверждения отправляется **только** по кнопке «Отправить письмо» на
`/resend-verification`. Регистрация, вход, открытие/обновление страницы и смена
email не отправляют письмо автоматически. После смены адреса подтверждение
сбрасывается; новый адрес нужно подтвердить через ту же кнопку. После успешного
подтверждения клиент перечитывает `/api/auth/me` и переходит в профиль; уже
подтверждённый аккаунт перенаправляется из экранов подтверждения в профиль.
Клиентский таймер повторной отправки дополняет существующие серверные ограничения.

| POST API | JSON | Результат |
| --- | --- | --- |
| `/api/auth/verification/request` | `{email}` | Нейтральный 202, повторное письмо |
| `/api/auth/verification/confirm` | `{token}` | Однократное подтверждение |
| `/api/auth/password/request` | `{email}` | Нейтральный 202, ссылка восстановления |
| `/api/auth/password/reset` | `{token,password}` | BCrypt, отзыв всех JWT |

Токены: 32 случайных байта SecureRandom, в БД только SHA-256; подтверждение живёт
24 часа, восстановление — 30 минут. Ссылка содержит fragment, который frontend
удаляет из адресной строки; открытие GET не расходует токен. Назначение, текущий
email, статус ACTIVE и версия сессий проверяются при погашении под блокировкой.
Замена токена, смена адреса/пароля, блокировка и logout могут сделать старую ссылку
недействительной. Сброс пароля также подтверждает владение указанным email.
После успешного reset cookie текущего браузера очищается, Context забывает
пользователя; ссылка «Вход» работает без принудительной перезагрузки страницы.
Запросы писем подавляются одинаково для известных/неизвестных адресов: раз в
минуту, максимум пять в сутки на адрес и назначение; IP — 30 запросов за 10 минут.

Локальный Mailpit принимает и показывает письма. Страницы:
`/forgot-password`, `/resend-verification`, `/verify-email`,
`/reset-password`. Для удалённого SMTP задайте MAIL_HOST, MAIL_PORT, MAIL_USERNAME,
MAIL_PASSWORD, MAIL_AUTH=true, MAIL_STARTTLS=true и MAIL_FROM. PUBLIC_APP_URL —
явный origin frontend (по умолчанию http://127.0.0.1:5173), не берётся из Host.
MAIL_HELO задаёт имя SMTP-клиента (culinary-craft.local); явные HELO и mail.from
предотвращают зависимость генерации писем от медленного определения hostname ОС.
SMTP-вызовы ограничены таймаутами 3 секунды. Письмо отправляется асинхронно после
commit; при сбое SMTP/перезапуске между commit и отправкой требуется повторный
запрос. Постоянной очереди с автоматическими повторами пока нет: сырые токены
на диск не записываются. Локальный Mailpit не является production-почтой.

JUnit подменяет SMTP и использует только изолированную БД. E2E читает реальные
тестовые письма из Mailpit, отправляет только на случайные адреса e2e.invalid;
нужны отдельная свежая E2E_DB_URL и локальный Mailpit. E2E_MAIL_PORT (1025) и
E2E_MAILPIT_URL (http://127.0.0.1:8025) позволяют выбрать тестовый Mailpit.

## Интерфейс и административное рабочее пространство

Главная, каталог, рецепт, редактор и аккаунт используют общие цвета, отступы,
контролы, состояния и диалоги. Заголовки публичных страниц оформлены как книга
рецептов; администрирование использует рабочую сетку с боковой навигацией.
Меню по аватару содержит профиль, настройки, администрирование для ADMIN и выход.
Меню поддерживает стрелки, Escape и закрытие снаружи. Модальные окна используют
нативный `dialog`, удержание фокуса и его возврат после закрытия.

«Мои жалобы» убраны из основной навигации и профиля. История и API сохранены
по `/reports`. На опубликованном рецепте жалоба открывается в модальном окне:
причина обязательна, описание необязательно (если заполнено — 10–1000 символов).
Активные дубликаты и ограничение пяти жалоб в час проверяются сервером.
Внутренние заметки не видны заявителю. Решение по жалобе не меняет рецепт или
доступ пользователя — это отдельные действия.

`/admin?section=reports|users|audit|recipes|storage|overview` — разделы управления.
Таблицы жалоб, пользователей и аудита имеют серверные страницы 10/20/50 строк,
общий счётчик и фильтры. Поиск пользователей выполняется по имени/email, жалоб —
по названию рецепта и имени/email заявителя. Аудит показывает русские названия
событий, имя администратора и подробности. Таблицы прокручиваются внутри своей
области; страница не расширяется на телефонах.

Совместимые расширения API (существующие значения по умолчанию сохранены):

- `GET /api/admin/users`: `role=USER|ADMIN`, `sort=name|email|registeredAt|status|role,asc|desc`
- `GET /api/admin/reports`: `sort=createdAt|id|status|recipeTitle,asc|desc`
- `POST /api/admin/recipes/{id}/unpublish`: `{reason}` (3–500 символов), только ADMIN.
  Переводит `APPROVED` в `PENDING`, сохраняет рецепт и пишет `RECIPE_UNPUBLISHED`
  в аудит в той же транзакции. Для публикации снова используется обычная модерация.

Локальные копии восьми исходных фотографий Unsplash находятся в
`frontend/public/images/recipes`; исходники и лицензия указаны рядом. Пользовательские
загрузки продолжают обслуживаться через MediaService. Новый интерфейс не меняет
JWT/CSRF, отзыв сессий, блокировки, правила очистки файлов и Flyway-миграции.

Дизайн и продуктовые решения описаны в [docs/ui-redesign.md](docs/ui-redesign.md).
Результаты проверок доступны в [итоговом отчёте](reports/final-audit.html)
и [матрице требований](docs/ui-redesign-verification.md).

### Черновики редактора

Редактор сохраняет изменённые поля через 400 мс после ввода и сразу при
подтверждённом уходе. Черновик живёт в профиле браузера, отдельно для каждого
аккаунта, нового рецепта и каждого редактируемого рецепта. Чтобы продолжить,
откройте тот же редактор и выберите «Восстановить черновик». Если изменённое
поле на сервере уже обновилось, редактор предупредит об этом перед
восстановлением. Проверьте форму перед отправкой.

Локальные файлы и временные или приватные ссылки на фото нужно выбрать заново.
Загрузка фото выполняется при отправке рецепта. Успешная отправка удаляет
соответствующий черновик. Для демонстрации на общем компьютере используйте
отдельный профиль браузера.

## Схема и миграции

Выбран Flyway: для небольшой схемы удобны обычные SQL-миграции, которые можно
прочитать и объяснить на защите. Spring Boot применяет их перед проверкой JPA.
Hibernate настроен на `ddl-auto=validate`, а не создание или изменение таблиц.

- `V1__create_persistence_schema.sql`: пользователи, рецепты, упорядоченные
  ингредиенты/шаги/теги, отзывы и избранное; внешние ключи, CHECK, UNIQUE и индексы.
- `V2__seed_demo_content.sql`: три прежних демо-пользователя, десять рецептов
  (восемь опубликованы), исходные отзывы и избранное.

Миграции выполняются один раз, их история хранится в `flyway_schema_history`.
Повторный старт не восстанавливает удалённые рецепты и не перезаписывает изменения.
Уже применённые миграции V1–V8 не редактируют: следующие изменения оформляют как
`V9` и далее. Данные старого in-memory процесса автоматически перенести невозможно.

Записи сервисов транзакционны. Изменение, удаление, модерация, отзыв и переключение
избранного блокируют строку рецепта на время транзакции. Отзывы и избранное имеют
уникальные пары пользователя и рецепта; удаление рецепта удаляет связанные записи.
Существующие DTO и REST-маршруты рецептов сохранены. Каталог использует CatalogQuery:
SQL WHERE, ORDER BY, LIMIT/OFFSET, COUNT, агрегаты рейтингов и EXISTS для избранного.
JPA получает только ID выбранной страницы; владелец загружается одним join,
ингредиенты/шаги/теги — пакетами по 30. Списки жалоб получают имена заявителей
одним дополнительным запросом вместо отдельного запроса на строку.

V8 добавляет search_text и транзакционные триггеры для названия, описания и тегов.
Порядок тегов и поиск подстроки сохранены, `%`, `_` и `!` обрабатываются буквально.
GIN pg_trgm обслуживает поиск, частичные B-tree — опубликованные рецепты по дате,
времени и категории; добавлены индексы рейтингов, административных очередей и
проверки ссылок на медиа. pg_trgm должен быть доступен в PostgreSQL; Flyway-роли
нужно CREATE на БД либо расширение должен заранее установить администратор.
См. [PostgreSQL pg_trgm](https://www.postgresql.org/docs/17/pgtrgm.html).

COUNT и содержимое каталога читаются в одном REPEATABLE READ снимке. При равных
значениях сортировки используется ID. Между отдельными HTTP-запросами offset-
пагинация может сместиться после вставки/удаления; постоянный снимок или cursor API
потребовал бы отдельного изменения контракта. Глубокие offset и поиск короче трёх
символов остаются более дорогими. На маленькой таблице PostgreSQL вправе выбирать
последовательное чтение вместо индекса. Личные списки `/mine`, `/favorites`,
`/pending` пока сохраняют прежний непагинированный контракт; массовое переписывание
RecipeStore не выполнялось. Это следующий отдельный шаг при росте данных.

На frontend число кнопок страниц ограничено, есть состояния ошибки/ожидания,
видимый фокус и перенос административных элементов на узких экранах. Проверки
включают SQL-выдачу при равных ключах, индексирование изменений тегов, ограничение
числа JPA-запросов, параллельный commit и мобильный Chromium 390 px.

## Проверка сохранения данных

1. Зарегистрируйтесь и создайте рецепт; войдите под bootstrap-администратором и одобрите его.
2. Добавьте рецепт в избранное и оставьте отзыв; запомните URL рецепта.
3. Остановите backend через Ctrl+C и снова выполните `.\gradlew.bat bootRun`.
4. Откройте тот же URL: рецепт, рейтинг, отзыв и избранное должны сохраниться.
5. Можно остановить PostgreSQL через `docker compose stop postgres`, затем
   запустить его через `docker compose up -d --wait postgres` и повторить проверку.

`docker compose down` сохраняет volume. Не используйте `down -v` для обычной
остановки: этот флаг удаляет данные базы.

## Автоматические проверки

Backend из `backend/`:

```powershell
.\gradlew.bat clean check bootJar
.\gradlew.bat test --tests 'com.culinarycraft.api.RecipeApiIntegrationTest'
```

JUnit использует Testcontainers с настоящим `postgres:17-alpine`, production
миграции и отдельные временные базы. Docker должен работать; локальный Compose
для JUnit не требуется. Тесты не переключаются на H2 и не пропускаются без Docker.
Версия Testcontainers закреплена на 1.21.4 через BOM Spring Boot: она исправляет
несовместимость Docker API 1.32 из версии 1.21.3 с новыми Docker engines в CI.
Сервисные/API-тесты изолированы откатом транзакций; отдельные тесты проверяют
конкурентные записи, ограничения БД, каскадное удаление и два последовательных
старта Spring-приложения с одной базой.

Frontend из `frontend/`:

```powershell
npm.cmd run lint
npm.cmd run test:ci
npm.cmd run build
```

Для E2E запустите отдельные PostgreSQL и Mailpit. Укажите свежую тестовую базу
в `E2E_DB_URL` и запустите из `frontend/`:

```powershell
npx.cmd playwright install chromium
npm.cmd run test:e2e
```

Для Firefox или WebKit установите нужные движки через
`npx.cmd playwright install firefox webkit` и задайте
`$env:E2E_BROWSER = 'firefox'` либо `'webkit'` перед повторным запуском
с отдельной свежей базой. По умолчанию используется Chromium.

Playwright сам запускает backend/frontend и использует настоящую БД. Он создаёт
аккаунты, рецепты и жалобы только в отдельной свежей БД из `E2E_DB_URL`.
Каталог изображений для E2E создаётся во временной папке ОС. Не используйте серверы другого проекта
на 8080/5173. В CI JUnit использует Testcontainers, а E2E — отдельный PostgreSQL service.

Прогон проверяет адаптивность на 375, 768, 1280 и 1920 px без снимков,
видеозаписи и трассировок. Пороги покрытия составляют 35% строк для JaCoCo
и 30% строк, выражений и функций для Vitest.
Отчёты: `backend/build/reports/`, `frontend/reports/frontend/`,
`frontend/playwright-report/`. Quality Gate по-прежнему требует успешных backend,
frontend, E2E и metrics. Release workflow не изменён.

Подход к миграциям и тестовым контейнерам соответствует
[документации Spring Boot](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html)
и [service connections](https://docs.spring.io/spring-boot/3.5/reference/testing/testcontainers.html).
