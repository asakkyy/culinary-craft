# Проверка исходной лабораторной работы №5

Основание: архив `culinary-craft.7z`, предоставленный пользователем, лабораторная работа №5 (отчёт), публичный репозиторий `asakkyy/culinary-craft`, состояние на 13.11.2026. У репозитория на GitHub есть история успешных и неуспешных запусков. Ограничение: приватные настройки Rulesets/Branch Protection из публичного просмотра недоступны; фактические новые проверки выполнятся только после push.

## Почему замечания преподавателя обоснованны

1. **Покрытие "сразу выводило":** в исходном `backend-ci.yml` HTML отчёт брали из ошибочной папки, а комментарий через сторонний Action публиковался только в PR при доступных правах, без гарантии. Теперь проценты отображаются прямо в логе Vitest и в Summary GitHub Actions, HTML/XML сохраняются.
2. **Тег только из main:** исходный `Auto Tag` срабатывал при push в main, но ещё до гарантий успешного выполнения тестов. Новый release workflow принимает только успешный завершённый `Quality CI` с событием `push` в `main`, проверяет точный SHA `origin/main`, делает аннотированный тег и GitHub Release. Вне workflow человеческому пользователю GitHub технически может позволить вручную создать тег: это отдельная задача правил доступа.
3. **Много подробных метрик:** реализован `scripts/collect_metrics.py`, который читает источники, а не подставляет фиктивные цифры.
4. **Отчёты в отдельных папках:** в скачиваемых артефактах есть сырые XML/JSON, отчёт каждого теста в `test-cases.csv`, замечания каждого линтера в `static-issues.csv`, HTML отчёты покрытия, сборки JAR и dist.
5. **Статические тесты и вывод:** Checkstyle для Java, ESLint и Prettier для React; источники лежат в `config/checkstyle` и `eslint.config.js`, результаты в `static/` и `metrics.csv`.

## Честные оговорки при сдаче

- Новый CI и релиз **не запускались на чужом репозитории** и значения покрытия по ним неизвестны до первого реального прогона.
- Предел 50% Java и 60% React — установленное условие прохождения, а не заявленный результат тестирования.
- Первый исторический запуск нового `Quality CI` не сможет честно показать его success rate за предыдущие этапы: статистика накапливается по мере запусков.
- Настройки репозитория и ограничения ручной публикации тегов нельзя полностью задать одним YAML; см. `GUIDE_GITHUB_RU.md`.
- После merge необходимо сделать реальные скриншоты: Summary/Artifacts, тесты, Coverage и Release. Из-за отсутствия доступа к настройкам аккаунта их нельзя заранее заполнить в отчёте без фальсификации.
